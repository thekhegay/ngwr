A defaultMode other than auto is applied by the service, so it takes effect once something injects WrTheme — a header toggle usually does, or inject it in the root component — and on a prerendered page by the pre-paint script below, given the same value.

The fix is a blocking script in <head>, above every stylesheet. wrThemePrePaintScript() emits one: it reads the persisted mode exactly the way WrTheme and WrStorage write it — the key prefix, the JSON envelope and the TTL — falls back to defaultMode, and for light or dark sets color-scheme on <html>. auto writes nothing. It is plain ES5 with no dependency on the app bundle, and every step is wrapped: a blocked localStorage (private mode, a sandboxed iframe) leaves the page on auto rather than throwing before anything has rendered. The docs site you are reading runs this same script, and a spec in the library pins the two to the same answers.

The document, though, has exactly one <html> — and that matters if you run two Angular applications on one page (a micro-frontend shell plus a widget). Each gets its own WrTheme, and the service applies its mode the moment it is constructed, so a second application becomes a writer simply by injecting it: last writer wins, and each resolved() keeps reporting its own answer. Exactly one application on the page injects WrTheme. The others need nothing: the scheme and the whole --wr-* layer live on the document, so their components are already themed. Code that needs the current scheme reads WrTheme.resolved in the application that owns it and hands the value on, rather than constructing a second owner.
