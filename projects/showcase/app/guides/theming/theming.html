Overlays follow the ROOT scheme, not the subtree's. A select, dropdown or dialog opened from inside renders its panel into the overlay container at the end of <body>, outside the element that set the scheme. When the panel has to match, hand it the scheme through the overlay's panelClass.

Overriding the bottom sheet takes an !important of your own, in a stylesheet that loads after ngwr's, at equal or higher specificity — that is the whole trick, and a rule on the BEM class without it simply does nothing. Twelve of the twenty are on .wr-overlay-sheet, the presentation dialog, select, dropdown and popover share on small viewports: eight on the sheet itself (width, min / max width, the two max-height declarations, the top-only radius, the keyboard lift and the slide-up animation) and four stretching its direct children and squaring their bottom corners. Reach for the sheet's own tokens first — --wr-overlay-duration and --wr-overlay-ease are read from var(), so a custom property beats the declaration without any specificity fight at all.

One of the twelve cannot be beaten by a plain rule at any specificity. margin-bottom on the sheet is fighting an inline style: all four sheet users pin the pane with a CDK GlobalPositionStrategy, whose apply() writes margin-bottom: 0px onto that very element on every reposition. The same is true of the three position declarations — .wr-context-menu-overlay, .wr-dialog-panel and .wr-drawer__panel each undo an inline position: static that CDK re-applies after attach. If you need different geometry there, change what the strategy is given rather than what the rule says: the panel width and the radius are ordinary declarations you can win.

A space-separated string is the point — an array works too, but the CDK hands an overlay's classes to classList.add() without splitting them, so a single 'p-4 rounded-xl' used to throw InvalidCharacterError and take the overlay down with it. Every hook here runs its value through toClassList first, which is exported for the same lists you build yourself. null and undefined mean "add nothing", so a hook bound to a signal that is not ready yet needs no guard.

What lands where is worth knowing before you write the rule. A pane is a positioning wrapper: for dialog and the drawer service the content IS the pane, so your classes paint the box, while for select, dropdown and the pickers the box that paints is inside it — so .my-class .wr-select-panel is the rule, not .my-class. The context menu is on the box itself, and the drawer component matches its service rather than its pane. Each input's JSDoc names its element.

This does not rescue an encapsulated component stylesheet. The element belongs to ngwr's view, so it carries no _ngcontent attribute of yours and a rule in your component's own .scss will not match it — the class has to be global, which is what a utility framework's classes already are. Where you want a value rather than a rule, the component's own --wr-* hook is still the shorter road, and every component page catalogues its own.
