Never target a 7.x, 8.x or 9.x release — not with ng update ngwr@7, @8 or @9, not with ng add, not with any ng g ngwr:*. Every release from 7.0.0 to 9.1.0 ships CommonJS schematics under a package.json that declares "type": "module", so Node loads them as ES modules and the command dies with exports is not defined in ES module scope. 10.0.0 fixed the packaging. The one command above never loads those files: the migrations it runs, v7, v8 and v9 included, are the ones shipped inside the release it installs. The “migrate each major version individually” refusal the Angular CLI prints is for Angular's own packages — it matches @angular/* and @nguniversal/* and nothing else — and does not apply to ngwr.

If an ng update ngwr@9 already failed with that error, it had moved package.json and your lockfile to 9.x when the migration step crashed, and nothing moved them back: the CLI restores package.json only when the install itself fails. A later ng update ngwr therefore starts from 9.x and silently skips the v9 migration — the <wr-checkbox> rename below, whose leftovers raise no error either. Do not count on reverting the bump: committing it, which is how most people get past Repository is not clean, makes it stick. Run the skipped step by name instead. It works however package.json was left. --name runs the migration shipped inside the release you installed and checks no version, and it rewrites only <wr-checkbox> bindings, which none of v12, v13 or v14 touches. A failed @7 or @8 leaves the same hole for that major, and for each later one you also tried: run each skipped migration the same way, oldest first.

If ng update ngwr hung on 14.5.0 or earlier, it was the v14 migration: up to 14.5.0 it could hang on an ordinary template, and the only way out was to kill the command. By then package.json was on 14.x and any earlier migration in that run had already written its changes, so the project looks upgraded, but the v14 renames were never applied and a later ng update ngwr skips them. Leftover closeable, totalItems, currentPage or wrSize bindings compile without an error. 14.5.1 fixed the hang. Run the skipped step by name; it rewrites the six renames, prints the v14 report again, and changes nothing in templates that are already migrated.

Two things that stop the first run, and neither is ngwr. Under pnpm 11 a fresh install can exit 1 with ERR_PNPM_IGNORED_BUILDS — its default is to refuse dependency build scripts until the workspace allows them — and a release published within the last day is held back by pnpm's minimum release age, so ng update ngwr can land on the previous patch and report nothing to do. Both are package-manager policy: allow the builds, or wait out the age window, then re-run. The migration itself is idempotent, so running it twice costs nothing.

Upgrading is also the moment to read the range you pinned. A breaking change can no longer arrive in a minor or a patch — the release script refuses that bump — so a caret range on a major is a safe range, which it was not when 12.2.0 shipped one. Versioning & support has that rule, how long the line you are leaving keeps getting security fixes, and what the open-ended Angular peer range does and does not promise.

The silent half is a var() at a token that no longer exists. It is invalid at computed-value time, so the browser drops the whole declaration holding it — a border: 1px solid var(--wr-color-light) draws no border at all, a background stays transparent — and nothing says so in the build, the console or a test. A dropped declaration is indistinguishable from a rule nobody wrote. This repository found 220 of them in its own docs site after the cut, across 71 files, with every one of its nine gates green. Every removed neutral token that has a successor is listed under the renames below — --wr-color-light, -dark, -medium, -muted-text, -outline and the three --wr-color-border* — so search your stylesheets and templates for every name in that list.

A removed intent in a template fails loudly, or not at all. With strictTemplates — the CLI default — a static color="secondary" is a compile error naming the five values that remain. Without it the string binds, the component writes a class no rule matches, and the element renders neutral in silence. Whether a secondary button should become primary, danger or a colour you declare yourself is a decision only you can make, and light / medium / dark were fills, so dropping the attribute to get the neutral variant is a visual change rather than a rename.

A compile-time rebrand has to drop the removed keys. A @use 'ngwr/theme' with ($base-colors: (…)) map still naming one of the four stops the Sass build with the key in the message. The neutrals are no longer seeded there at all: they are the gray ramp, and each theme sets its own six steps rather than mirroring the other's.

A selector keyed on the attribute matches nothing, and says nothing. Every [data-theme='dark'] rule in your CSS, every @include theme.dark, every theme.dark-selector() and every with ($theme-attribute: …) has to go: the mixins and the variable are removed, so those are build errors, while a hand-written selector compiles and quietly stops applying. Write the dark value beside the light one with light-dark() instead. It takes colours only — light-dark(1px, 2px) is invalid — and it works in a component stylesheet as written, with no :host-context() twin.

provideWrTheme() is removed. WrTheme is root-provided and keeps its API — mode, resolved, set(), toggle() — so delete the call; to change defaultMode or storageKey, provide WR_THEME_CONFIG instead. The attribute option is gone from both the config and wrThemePrePaintScript(), which now writes color-scheme on <html> for a stored light or dark choice, or for a non-auto defaultMode passed to it, and nothing for auto. Code that read the attribute reads WrTheme.resolved().

Without the provider, nothing creates WrTheme at boot. provideWrTheme() did, and that is what applied a stored choice and a non-auto defaultMode on the first screen. Now both apply when WrTheme is first injected, so an app whose toggle sits behind a lazy route follows the OS until that route opens — silently. Inject it once at boot, in the root component or with provideEnvironmentInitializer(() => inject(WrTheme)), or ship wrThemePrePaintScript() with the same options, which also lands before the first paint of a prerendered page.

Forcing the page's scheme yourself is fine. <html style="color-scheme: dark">, or the same property written from your own code, holds alongside WrTheme: in auto the service leaves an author-written value alone, and only a light or dark mode — picked, stored or configured — writes over it.

Every -rgb channel token is removed — the intents', the neutrals', the backdrop's and the component hooks --wr-calendar-accent-rgb and --wr-color-picker-rgb. A var() at one is invalid at computed-value time, so the declaration holding it is dropped in silence, like the removed neutrals above. Mix the colour toward transparent instead: the alpha becomes the percentage, and it paints the same. The scrim's channel has a colour token now, --wr-color-backdrop; the calendar's is --wr-calendar-accent itself; the picker's is --wr-color-picker-color, a whole colour.

Code that reads a token in TypeScript gets the declared text. getPropertyValue('--wr-color-primary') returns light-dark(…) unresolved, and a canvas cannot paint that: a 2D context refuses it, and Firefox accepts it and always paints the light side. Hand a canvas the colour the cascade computes instead, with resolveCssColor from ngwr/utils.

Three bits draw differently in dark. Their dark-only rules are gone with the attribute, and a blend mode, a length and a strength are not colours, so light-dark() cannot switch them: each now has one value for both schemes. --wr-star-border-stop is removed: the ray's fade is fixed, a 10% / 16% tail in light and 10% in dark, so an override of it does nothing — set the ray's background on .wr-star-border .wr-star-border__ray instead, two classes because the component's own stylesheet loads after yours. wr-border-glow's --wr-border-glow-halo-blend, -fill-blend and -fill-scale default to normal, normal and 0.25 in both schemes, where dark used plus-lighter, soft-light and 1; and the wr-tilt-card glare blends normally, where dark used 25% white under overlay. To bring the old dark look back, set those yourself on a page or section you know is dark.

The runtime palette is removed: wrThemeTokens(), wrIntentTokens(), wrContrastFor() and the theme builder page that used them. Rebrand at build time, through $base-colors, or theme.rebrand() on :root or a subtree — see Theming.

The browser floor rises to the one light-dark() sets: Chrome 123, Firefox 120, Safari 17.5. Below it every colour that differs between the schemes resolves to nothing.

The list renders nothing until you migrate, which reads as empty data rather than as a missed step — so search for every <wr-sortable-list> that still holds an <ng-template>.

In an Angular CLI app ?raw needs "loader": { ".svg": "text" } in the build options and a declare module '*.svg?raw' { const svg: string; export default svg; }. Or skip the build option: import the file as import plusSvg from 'feather-icons/dist/icons/plus.svg' with { loader: 'text' }; and declare '*.svg' instead.

A Feather glyph no longer carries wr-icon__svg: its files bring their own feather feather-<name> classes. Inside <wr-icon> it renders the same, so only a stylesheet of yours that reached the glyph through that class needs .wr-icon svg instead.

ngwr/squircle was deprecated in v14 and is removed. Use shape="squircle" on <wr-btn>, <wr-avatar> and <wr-badge>, or the smooth-br mixin from @use 'ngwr/theme' anywhere else. They are not the same thing: the native corner-shape falls back to a plain rounded corner where a browser has not shipped it, and it takes no radius, smoothing, corners or border inputs. An import or an @use fails the build; a leftover wrSquircle attribute is inert and silent.

<wr-action-sheet> is removed, with its test harness. ngwr is not a mobile library, and the sheet was a preset over <wr-drawer position="bottom" rounded> — two of its three ingredients went with it. Write the drawer directly; the rows, their order and the cancel group are markup only you have.

<wr-drawer showHandle> is removed, and swipe-to-dismiss with it, for the same reason. The drawer still closes on the backdrop, on Escape, and through its own dismiss button (closable, on by default) — so for most drawers deleting the attribute is the whole migration. A bound [showHandle] is a compile error; a bare one is inert, so search for it.

A field that leaned on ngwr's sentences is silent now. It is still marked invalid, with aria-invalid on the control, and shows no message. Dev mode logs one warning per field and key naming the three ways to supply one; a production build says nothing, so search for every <wr-form-field> without a <wr-form-error> and give each of its errors a source.

A provideWrFormErrors() map moves into your catalog, as a validation namespace in each locale your loader serves. A function message becomes a template whose params are the error payload, so requiredLength reaches a minlength sentence as a placeholder. The field label a function could read has no equivalent: a sentence that names its field goes on that field's validator as { message }.

The date picker's refusals have no English default. <wr-date-picker> and <wr-date-range-picker> word a refused entry from validation.dateFormat, minDate, maxDate and dateFilter in your catalog, with the example date as the example param. Without those keys a refusal still shows as a danger border and aria-invalid, with no sentence.

The import fails the build. Deleting the call is what is silent: every control it reached goes back to its own default — md and the standard radius — so bind each key the call set before you remove it. An editor or markdown key has nothing left to bind; the markdown section below says what replaces both.

A named key has to become its width: md is (min-width: 768px), and the rest of the map is the $breakpoints list in ngwr/breakpoints. A query string matches() accepted passes to observe() unchanged. Both answer false on the server, so a template that branched on one prerenders the same arm it did. current() has no equivalent: observe the widths you branch on and pick the largest that matches.

The import, the @use and the harness calls fail the build, and so do a bound [responsive] and an inline { responsive: true }. A bare responsive attribute is inert, and a rule on .wr-overlay-sheet, .wr-overlay-backdrop or .wr-command-palette--sheet matches nothing, so search for both.

The imports fail the build. A token format written for date-fns does not. That adapter handed a [format] pattern to date-fns untouched, while the native one reads yyyy yy MMMM MMM MM M dd d HH H hh h mm ss a and prints anything else verbatim, so EEEE or PPP reach the field as letters, and do as 15o. A named format (shortDate, time, …) prints through Intl now, so its exact string can change as well. The Luxon adapter translated the native tokens but handed every other letter to Luxon, so a Luxon-only token (EEEE, ccc, DDD) now prints verbatim too, and MMMM beside a day token is declined where Luxon printed the standalone form.

An adapter of your own implements what WrDateAdapter declares abstract: today, clone, createDate, isValid, the getters from getYear to getSeconds, addYears, addMonths, addDays, setTime, isSameDay, isSameMonth, compareDate, format, parse, getFirstDayOfWeek, getDayOfWeekNames and getMonthNames. Months are 0-based, as on Date, and parse has to read back whatever format printed for the same key; returning null refuses the input and leaves the committed value alone. Configuration has the skeleton.

An app that stores HTML or markdown converts at its own boundary, in both directions: the tree is ProseMirror's own toJSON() shape, so a ProseMirror Schema declaring the same nodes, with DOMSerializer and DOMParser from prosemirror-model, reads and writes it. A read-only editor renders a stored document without mounting ProseMirror, which is what most <wr-markdown> uses become.

The imports, the @use and a bound [format] fail the build. A static format="…" is inert, and an HTML or markdown string that reaches value untyped is refused like any value the editor cannot read: the editor stays empty and read-only with wr-editor--refused, and only dev mode says why. A form model whose editor field started as '' starts as null now.

The imports fail the build. A var(--wr-keyboard-inset, 0px) does not: it falls back to its default and stays there, so search your stylesheets for it.

A bare call left in place breaks nothing: it registers the same adapter. One thing renders differently. A wrDate pipe in an app that never provided an adapter used to fall back to Intl's dateStyle / timeStyle shorthands, and now formats through the native adapter, so shortDate prints 3/15/2026 where it printed 3/15/26 and time prints 02:30 PM where it printed 2:30 PM (the date-time keys change the same way), and a token string such as 'dd.MM.yyyy' is honoured where it used to fall back to shortDate.

<wr-loading-bar> no longer follows the router. The subscription is opt-in now — add provideWrLoadingBarRouter() from ngwr/loading-bar/router to your application providers. Without it the bar still works for manual start() / complete() and simply never moves for a navigation. Nothing throws, nothing warns, and the bar renders exactly as it did before: it just stays at 0%. This project's own site shipped an empty bar for the length of a release by missing precisely this. ng update lists every file that renders one.

A translated pagination.of stops being read. The whole “1–10 of 235” line is one pagination.range template now, so a catalog that still defines of keeps a key nothing looks up — and that one line reverts to English while every other string in the same catalog goes on working, which is the version of this bug that survives a review. Replace it with pagination.range and pagination.compact, whose shapes are in the diff below. common.of is a different key and is untouched — it is still shipped, and still unread.

A date the field cannot parse now returns null instead of a wrong date. The one change here with no codemod entry at all, because there is no token to detect. It turns a wrong answer into no answer, so a host that relied on new Date()'s leniency sees the committed value stay put where it used to change — and a value that stays put looks like a user who has not finished typing. Its own section below has the detail; read it if any date in your app is typed rather than picked.

Two things the codemod cannot reach. A component class reading one of these off a viewChild() reference is a type error on upgrade, which is the loud failure and needs no help. The quiet one is a test: WrWindowHarness.getChromeSize() answers 'sm' / 'md' now, so an assertion on 'compact' fails as a wrong value rather than as a wrong type. The pagination harness filter moved with its input — WrPaginationHarness.with({ currentPage: 3 }) becomes { page: 3 } — and that one the codemod does rewrite.

One correction, because the release notes said otherwise: v13 announced this rename and did not make it — its subject line reads “input size loses its prefix” while wrSize shipped unchanged in 13.0.0 and 13.0.1. It lands here, in v14. If you already followed that note and wrote size on a v13 input, nothing broke loudly: size is a legal native attribute, so the template compiled and the control quietly fell back to md. On v14 the same markup means what it says.

The date entry points nest under `ngwr/date`. `ngwr/icon` already nested its implementations at `ngwr/icon/adapters/lucide` and `…/feather` (v15 later removed both), while the date ones were flat and hyphenated — one idea spelled two ways depending on which feature you reached for. Only the import specifier changes: every exported symbol keeps its name, and these entry points ship no styles, so no `@use` path moves with them. v15 later removed the two library adapters, leaving `ngwr/date` and its native one.

`readI18nText()` returns `Signal<string>`. Add `()` at every read. This is a fix rather than a refactor, and the reason matters if you have ever wondered why a component announced itself in the wrong language: `WrI18n` writes every loader-backed catalog from a promise, which resolves a microtask AFTER the first change-detection pass — so the old one-shot read froze the ENGLISH fallback for the life of the app. A `<wr-date-picker>` said “Открыть календарь” on the field and “Open calendar” on the button beside it, off the same key. A synchronous read cannot be correct against an asynchronous catalog, so the type had to move. Only affects code that calls the helper directly; the `wrT` pipe, the `[wrT]` directive and `useI18nText` are unchanged.

`<wr-checkbox>` — `value` is now `checkboxValue`. The checkbox became a signal-forms native `FormCheckboxControl`, whose contract reserves `value` for the form value — so its boolean state is the `checked` model, and the group-membership identity moved to `checkboxValue`. Watch out: the static form fails silently. `<wr-checkbox value="x">` raises no template error, it just lands as a plain DOM attribute, leaving every child of the group with the same `null` identity — so they all toggle together. The codemod rewrites `value` / `[value]` / `[(value)]` scoped to the `<wr-checkbox` tag, and deliberately leaves `<wr-checkbox-group>`'s own `value` alone.

Lucide icon names register verbatim. `lucideIcons()` no longer kebab-cases its keys, so a `chevronDown` key now registers as `chevronDown`, not `chevron-down`. No codemod — and nothing errors, the icon simply stops rendering. Either quote the key or update the usages.

`info` added to `WR_COLORS` / `WrColor`. Additive at runtime, but it widens the union — an exhaustive `switch` over `WrColor` without a `default` will stop compiling until you handle the new member.

Density values renamed. `compact` / `default` / `comfortable` become `sm` / `md` / `lg`; `touch` is unchanged and `md` is now the default. Affects `provideWrDensity`, the `wrDensity` directive, and the `[data-wr-density]` selector.

Pagination sizes trimmed. `WrPaginationSize` drops `xs` and `xl` — it is now `'sm' | 'md' | 'lg'`.

Removed components. `WrReveal` (the `wrReveal` directive in `ngwr/directives`) and `WrScrambleText` (`ngwr/scramble-text`) were removed — both were unreliable. There is no drop-in replacement; the codemod lists every file that uses them so you can swap them out.

Key renames: `wr-autocomplete` / `wr-chips-input` → `wr-select` (with `mode`); `wr-time-picker` / `wr-date-time-picker` → `wr-date-picker`; `wr-tooltip` → `wr-popover`; `wr-tree-select` → `wr-tree`; `wr-bottom-sheet` → `wr-drawer`; `wr-image` → `wr-lightbox`; `ngwr/tag` → `ngwr/badge`; `wr-animated-text` → `wr-typewriter` / `wr-decrypt-text` / `wr-split-text` (per mode).
